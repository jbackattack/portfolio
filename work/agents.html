AI test agents

Three QA agents my team built on the company's shared agent framework, and the automation prototype that came first.

Role
Designed the automation prototype; my team built the live agents
Stack
Appium, Java, TestNG, Bitrise, LambdaTest, GitHub Copilot, BigQuery CLI
Status
Three agents built and deployed; the prototype did not ship

What shipped

The infrastructure team built a shared agent framework, so everyone in tech made agents the same way in one shared workspace. My team built three agents on it:

  • Test case analyzer. Reviewed my team's existing test repos against best practices.
  • Test case creator. Wrote new tests from a pull request, following those same best practices, so new work didn't repeat old problems. It saved my QA engineers hours, and often days, compared with building the same set of tests by hand.
  • Mobile data lookup. Answered plain-text questions about mobile app data by running queries with the BigQuery command-line tool, so nobody had to wait for a new dashboard.

The analyzer set the standard for the existing tests, and the creator built new ones to meet it.

First run

The analyzer found security problems right away, including passwords stored in insecure places in the test code.

Why a data lookup agent

I used to rely on the data team to build Looker dashboards for the mobile data I needed. Those dashboards went stale, and they needed constant updating because I was always asking for different data.

So I set up the BigQuery command-line tool and built an agent on top of it. From then on I could ask a question in plain text in VS Code, through the agent manager, and the agent ran the query.

There was a bonus. Queries the data team ran for me sometimes uncovered bugs, because the data came back undefined when an out-of-date library wasn't sending it. Being able to ask more questions, more often, made it easier to catch problems like that.

Why the prototype didn't ship

The automation prototype was first written up as a GitHub extension, and it was designed while the shared framework was still being built. Once the infrastructure team's live agent setup existed, we decided to build on it instead of shipping a separate system, so the prototype never went to production. What carried over was the process, not the code: QA rated the risk, AI drafted the tests, and people approved them before anything shipped. Only where the agent lived changed.

Where it started: the automation prototype

The problem

My team was checking mobile cards by hand. That didn't keep up with an app on two platforms, so we moved toward nightly smoke suites and AI-generated tests.

AI can write a lot of tests quickly. The risk was a pile of tests nobody trusted. The prototype was built around one rule: a person with risk judgment decided what got generated and what got approved.

How it works

  1. Receive a PR

    QA picks up the pull request that needs test coverage.

  2. Prompt the agent

    QA asks the agent to assess the risk and generate tests, with limits set by the risk.

  3. Review

    QA reviews the tests and approves them or sends them back.

  4. Merge

    Approved tests go into the test repo as a separate PR.

  5. Run

    Appium suites run on Bitrise against LambdaTest devices.

A simplified view of the framework.

Design decisions

  • QA is the approval gate. AI proposed and QA decided, so the team trusted what ran.
  • Generation limits follow risk. Effort went where a failure would cost the most, instead of generating tests everywhere.
  • A single delivery lane. One path from change to release kept ownership clear.
