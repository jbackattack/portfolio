AI test agents

Three QA agents my team built on the company's shared agent framework, and Spark, the prototype that came first.

Role
Designed Spark; my team built the live agents
Stack
Appium, Java, TestNG, Bitrise, LambdaTest, GitHub Copilot
Status
Three agents built and deployed; Spark was a prototype

What shipped

The infrastructure team built a shared agent framework (UDF), so everyone in tech makes agents the same way in one shared workspace. My team built three agents on it:

  • Test case analyzer. Reviews my team's existing test repos against best practices. On its first run it found security problems, including passwords stored in insecure places in the test code, so it paid off right away.
  • Test case creator. Writes new tests that follow those same best practices, so new work doesn't repeat old problems.
  • Mobile data lookup. Looks up mobile app data for the team.

The analyzer sets the standard for the existing tests, and the creator builds new ones to meet it.

Where it started: Spark

The problem

My team was checking mobile cards by hand. That doesn't keep up with an app on two platforms, so we moved toward nightly smoke suites and AI-generated tests.

AI can write a lot of tests quickly. The risk is a pile of tests nobody trusts. Spark was built around one rule: a person with risk judgment decides what gets generated and what gets approved.

How it works

  1. Trigger

    One of three modes starts a run.

  2. Assess risk

    QA rates how much a change could hurt.

  3. Generate

    AI drafts tests, with limits set by the risk.

  4. Approve

    QA approves the tests or sends them back.

  5. Run

    Appium suites run on Bitrise against LambdaTest devices.

A simplified view of the framework. Confirm the step order before publishing.

Design decisions

  • QA is the approval gate. AI proposes and QA decides, so the team trusts what runs.
  • Generation limits follow risk. Effort goes where a failure would cost the most, instead of generating tests everywhere.
  • A single delivery lane. One path from change to release keeps ownership clear.
  • Three trigger modes. Different situations start a run in different ways, without separate processes.
  • GitHub Copilot as the model. It was the LLM my company had approved, so the design worked inside existing rules.

What I delivered

  • A 13-file agent framework, fully specified.
  • A Jira epic with eight to nine child stories, ready for engineering to pick up.
  • A comparison of two ways to run the agent: a Bitrise step and a GitHub Copilot extension in IntelliJ.
  • Onboarding documentation for a Test Quality Agent that runs in IntelliJ through Copilot Chat.
